# E2E-тесты (Playwright)

Интеграционные тесты поверх реально собранного стека — сервер + Postgres +
веб-клиент, без моков. Не заменяют юнит-тесты в `server/`, `agent/`,
`android/`, `desktop/` (те проверяют логику компонентов), а проверяют, что
основные пользовательские сценарии реально работают в связке: регистрация,
активация тарифа, устройства, пополнение баланса, логаут/логин с сохранением
сессии. Стандаловый npm-проект, как `agent/`, `web/`, `desktop/`.

## Разовая настройка

```bash
cd e2e
npm install
npx playwright install chromium   # скачивает сам браузер, не в git
```

## Перед запуском — поднять стек

```bash
docker compose up -d postgres
./gradlew :server:bootRun          # HTTP :8080, gRPC :9090
cd web && npm run dev               # :3000, проксирует /api на :8080
```

## Запуск

```bash
cd e2e
npm test            # headless в CI (переменная CI), headed локально по умолчанию
npm run test:headed # принудительно с видимым окном браузера
npm run test:ui     # интерактивный UI-раннер Playwright — удобно для отладки
```

По умолчанию тесты бьют в `http://localhost:3000` (dev-сервер веба). Чтобы
вместо этого проверить именно собранный статический бандл, который реально
уходит в прод внутри JAR сервера (`copyWebDist` + `bootJar`):

```bash
E2E_BASE_URL=http://localhost:8080 npm test
```

## Что покрыто

- `tests/landing.spec.ts` — публичная посадочная страница без логина:
  видны тарифы (регресс-тест на реальный баг: `GET /api/v1/user/tariffs` не
  был в `permitAll` в `SecurityConfig`, и цены на лендинге были пустыми у
  любого анонимного посетителя), переключение языка ru/en.
- `tests/full-user-flow.spec.ts` — один сквозной сценарий одним `test()` с
  шагами `test.step()` (не отдельными `test()` — у каждого своя изолированная
  `BrowserContext`/`localStorage`, а здесь именно один и тот же браузерный
  сеанс должен пронести токен через весь флоу): регистрация → активация
  бесплатного пробного тарифа (баланс $0, специально выбран, чтобы не
  зависеть от реальной оплаты) → добавление и отзыв устройства → генерация
  TRC-20 инвойса на пополнение → логаут → повторный логин с тем же аккаунтом
  и проверкой, что активная подписка никуда не делась.

## Ограничения

- Нода (`agent/` + реальный `xray-core`) не поднимается и не проверяется
  этим набором — Playwright управляет браузером, а не VPN-туннелем;
  фактическое соединение через VLESS/Reality здесь не тестируется никак.
- Платежи не проверяются по-настоящему (реальных TRC-20/EVM переводов тест
  не делает) — только то, что инвойс генерируется и показывается в UI.
- Каждый прогон регистрирует нового пользователя (`e2e-<timestamp>-<rand>@example.com`)
  — тестовые аккаунты копятся в БД, это осознанно (не полагаемся на
  сброс состояния между прогонами); для локальной БД это не проблема.
