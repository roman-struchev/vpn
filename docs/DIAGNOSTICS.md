# Сбор ошибок с нод и клиентов

Раньше сбой жил только в логе той машины, где произошёл: краш приложения на
чужом телефоне не видел никто, а падение xray на ноде — только тот, кто в
нужный момент читал `docker logs`. По проводу ходила лишь `conn_telemetry`,
которая считает успешные/неуспешные подключения и ничего не говорит о том,
**что** сломалось.

Теперь ноды и клиенты отправляют свои ошибки на сервер, а сервер отдаёт их
одним структурированным документом — в том виде, в котором его можно сразу
дать на анализ (в том числе LLM: «что ломается и надо ли что-то править»).

## Как получить отчёт

```bash
# Нужен админский токен (эндпоинт под /api/v1/admin/**)
curl -s -H "Authorization: Bearer $ADMIN_TOKEN" \
  "$SERVER/api/v1/admin/diagnostics/report?hours=24" | jq .

# Параметры: hours (по умолчанию 24), source (NODE_AGENT|ANDROID|DESKTOP|WEB|SERVER),
# limit (по умолчанию 50, максимум 200)
curl -s -H "Authorization: Bearer $ADMIN_TOKEN" \
  "$SERVER/api/v1/admin/diagnostics?hours=168&source=NODE_AGENT" | jq .
```

`/report` — тот же документ плюс короткая преамбула, объясняющая, что означают
числа; её и стоит передавать модели вместе с данными, чтобы не объяснять
схему отдельно. `/api/v1/admin/diagnostics` — только данные.

Что внутри: `totalOccurrences`, `distinctIssues`, разбивка по источникам и
компонентам и список `issues`, отсортированный по частоте. Каждый элемент —
**одна проблема, а не одно её проявление**:

| Поле | Смысл |
|---|---|
| `occurrences` | Сколько раз сообщили об этой проблеме |
| `reporters` | Примерно со скольких разных машин — отличает «одна нода в цикле» от «у всех» |
| `appVersions` | На каких сборках встречалась, от старых к новым |
| `sampleDetail` | Стек/вывод последнего проявления |
| `sampleContext` | Контекст последнего проявления (ОС, транспорт, код выхода…) |
| `firstSeenAt` / `lastSeenAt` | Когда началось и когда было в последний раз |

## Почему хранится агрегировано

Сообщения приходят с машин, у которых уже что-то не так: агент в краш-цикле
способен выдать тысячи сообщений в минуту. Поэтому строка в
`diagnostic_events` — это одна проблема, ключом служит отпечаток (sha256) от
источника, компонента, кода и **замаскированного** текста ошибки. Инцидент
стоит одной строки и счётчика, а не тысячи строк.

Маскирование (`<ip>`, `<uuid>`, `<email>`, `<hex>`, `#` вместо чисел) — это и
то, что вообще делает агрегацию возможной: «dial tcp 10.0.0.1:443 failed» и
«dial tcp 203.0.113.9:443 failed» — одна и та же проблема. Побочный, но
намеренный эффект: идентификаторы и адреса в базу не попадают.

Границы объёма — на всех уровнях:

- клиент/агент: буфер на 30–50 проблем, повторы схлопываются, при переполнении
  вытесняется самое старое, и об этом сообщается в самих данных
  (`REPORTS_DROPPED`) — счётчик не занижается молча;
- запрос: не больше 20 событий (`MAX_EVENTS_PER_REPORT`), все поля обрезаются;
- сервер: клапан на источник в минуту (`MAX_EVENTS_PER_SOURCE_PER_MINUTE`);
- `DiagnosticsPruneTask`: хранение 14 дней и потолок 2000 строк, вытесняются
  давно не встречавшиеся.

## Как сообщать о новой ошибке

Правило для всех трёх реализаций одинаковое: вызов делается из кода, который
**уже** в состоянии сбоя, поэтому он не бросает исключений, не блокирует и не
превращает цикл повторов во флуд.

```ts
// agent/ (нода)
import { reportError, reportWarning } from '../utils/diagnostics.js';
reportError('xray', 'XRAY_EXITED', `Xray exited with code ${code}`, err, { exitCode: String(code) });
```

```ts
// desktop/ (main-процесс)
import { reportError } from '../diagnostics';
reportError('vpn', 'PROFILE_LOAD_FAILED', 'Failed to load the VPN profile', e);
```

```java
// android/
import com.vpn.android.diagnostics.DiagnosticsReporter;
DiagnosticsReporter.error("vpn", "TUNNEL_START_FAILED", "Tunnel start failed", e);
```

`component` — подсистема (`xray`, `vpn`, `api`, `relay`, `proxy`), `code` —
стабильная метка вроде `XRAY_EXITED`: именно она, а не формулировка, держит
проявления одной проблемы вместе. Непойманные исключения и отклонённые
промисы перехватываются автоматически во всех трёх компонентах.

## Каналы доставки

- **Ноды** шлют по уже существующему gRPC-потоку (`AgentMessage.diagnostics`):
  поток аутентифицирован, `node_id` на нём уже известен, поэтому агент может
  сообщать об ошибках только от своего имени и ему нечем аутентифицироваться
  по HTTP.
- **Клиенты** — `POST /api/v1/client/diagnostics`, намеренно без токена:
  «не удалось получить токен» само по себе стоит того, чтобы об этом узнать.
  Безопасность этого канала обеспечивают лимиты сервера, а не доверие к
  вызывающему; эндпоинт всегда отвечает 200 и числом принятых сообщений,
  чтобы отправитель не ушёл в повторы из-за своей же диагностики.

## Что не отправляется

Ничего, что идентифицирует человека. `reporterId` — это UUID установки (тот
же, которым приложение и так аутентифицируется), то есть машина, а не
пользователь. Текст ошибки — это текст ошибки, и сервер ещё раз вычищает из
него адреса, почты и идентификаторы при приёме. Читать собранное может только
администратор.
