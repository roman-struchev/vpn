# P2P-ретрансляция: подключение через других участников

Раньше в проекте была реализована только одна половина: устройство могло
**отдавать** себя как реле (`desktop/src/main/p2p/relayAgent.ts`,
`android/.../P2pRelayAgent.java`, `agent/src/p2p/relay-session.ts`). Второй
половины — той, что **подключается** через реле, — не существовало ни в одном
клиенте, поэтому сервер вообще не выдавал p2p-ноды, а сама фича только тратила
батарею тех, кто её включил. Теперь она работает целиком.

## Два способа использовать пира

Пир всегда делает ровно одно: открывает обычное TCP-соединение по адресу,
который назвал клиент, и перекачивает непрозрачные байты через WebRTC
DataChannel. Разница — в том, какой адрес называют.

**Путь до ноды (реле).** Адрес — наш обычный VPN-сервер. Сессия VLESS/Reality
устанавливается между локальным xray-core и самой нодой, пир переносит уже
зашифрованный поток и знает лишь один адрес. Страна выхода не меняется: через
пира в Черногории можно подключиться к ноде в Финляндии, выход останется
финским. Включается автоматически, когда сеть блокирует прямой доступ.

**Точка выхода (P2P-выход).** Адреса — сайты, которые открывает пользователь,
и в интернет трафик выходит с IP пира, без нашей ноды в пути вообще. Это
пользователь выбирает сам: строка с пометкой P2P в списке подключения, только
на платных тарифах. Подробности — в разделе «Выход через пира» ниже.

В обоих случаях пир не видит содержимого. В режиме выхода он, однако, видит
адреса назначения и является тем IP, который видят сайты — это осознанное
решение владельца, принятое вопреки рекомендации
`docs/research/P2P_RELAY_FEASIBILITY.md` §2; аргументы обеих сторон там и в
§8.9.

## Как это устроено

```
xray (локально) → 127.0.0.1:<порт моста> → WebRTC DataChannel → реле → TCP → VPN-нода
```

1. Клиент запрашивает `GET /api/v1/user/p2p/relays` — список доступных
   участников. В нём нет ни адреса, ни имени хоста, ни владельца: только
   `nodeId`, регион и загрузка. До устройства добираются по WebRTC, а не по
   адресу.
2. На каждое соединение, которое xray открывает к локальному мосту, клиент
   создаёт свою сессию: DataChannel + SDP-offer, в котором **назван адрес
   ноды**, куда реле должно подключиться.
3. Сигналинг идёт через сервер-брокер: `POST /p2p/nodes/{id}/signal` отдаёт
   пакет реле, `GET /p2p/sessions/{id}/signals` длинным опросом забирает ответы.
   Брокер **складывает** сигналы реле в очередь сессии: реле отвечает SDP, а
   следом сыплет ICE-кандидаты, и без очереди все кандидаты после ответа
   терялись — именно они и нужны для прохождения NAT.
4. Когда канал открылся, мост читает локальный сокет и гонит байты в обе
   стороны. Раньше открытия из сокета не читается ничего: реле дозванивается до
   ноды только в этот момент, и всё отправленное раньше оно бы отбросило.
5. Обе стороны сообщают перенесённый объём (`/sessions/{id}/traffic-report` от
   клиента, `p2p_traffic_report` от реле) — кредит начисляется владельцу реле
   только когда оба отчёта сходятся.

## Когда включается

Автоматически — там, где клиент раньше сдавался: все ноды перепробованы на всех
транспортах, и проба цензуры показывает, что мешает сама сеть
(`OPERATOR_BLOCK_DETECTED`). Это ровно та ситуация, ради которой фича и
существует. Пробуются три пира; если ни один не подошёл, пользователь по-прежнему
видит честный экран «оператор блокирует».

Статус при этом говорит «через участника сети» / «via peer»: путь идёт через
чужое устройство и обычно медленнее, выдавать его за обычное подключение было бы
нечестно.

## Выход через пира

```
xray (локально) → 127.0.0.1:<порт моста> ──SOCKS5──┐
                                                    ├→ WebRTC → пир → TCP → сайт
       (своя сессия на каждое соединение) ──────────┘
```

Отличий от схемы выше три, и все три — следствие того, что адрес назначения
теперь у каждого соединения свой:

1. **Мост говорит SOCKS5.** Цель берётся из каждого запроса, а не фиксируется
   при старте, поэтому один пир обслуживает все сайты сессии. Ответ «успех»
   отправляется только когда DataChannel действительно открылся: более ранний
   ответ заставил бы xray поверить в соединение, которое ещё может не
   состояться, и недоступный пир превращался бы в зависший запрос вместо
   быстрого перехода к следующему.
2. **VLESS-outbound нет.** Нашей ноды в пути нет, говорить Reality не с кем;
   хоп до пира шифрует DTLS самого WebRTC. UDP заблокирован явным правилом:
   пир умеет только TCP, и иначе QUIC выглядел бы доступным и молча пропадал.
   DNS не страдает — он на DoH, то есть по TCP.
3. **Строка в списке различается по ключу, а не по названию.** Одна страна
   может быть в списке дважды — наши серверы и пиры там же, — поэтому
   `SubscriptionExportService` отдаёт для P2P-строки ключ `p2p:<регион>`, и
   именно ключ клиент сохраняет как выбор (`shared/regionKey.ts`,
   `util/RegionKey`).

Доступ решает тариф, а не пул ноды: на платном строка выбираема, на бесплатном
показывается с замком — тот же upsell, что у платных регионов. `GET
/api/v1/user/p2p/exits?region=` на пробном тарифе отвечает пустым списком, а не
ошибкой.

Пиры пробуются сверху вниз (не больше трёх): это телефоны, и уход в офлайн
посреди попытки — норма. Если не подошёл никто, клиент подключается к нашим
серверам и поднимает флаг `regionFallback` — интерфейс говорит, что выбор не
сработал, вместо того чтобы молча сменить пользователю страну и тип выхода.
Если пир отвалился уже в работающей сессии, клиент ищет другого в той же
стране и ждёт с повторами, а не переезжает на наши серверы: выбор пользователя
сохраняется.

Трафик такой сессии не проходит ни через одну нашу ноду, поэтому обычный учёт
её не видит. Клиент помечает отчёт `exit: true`, и сервер списывает байты с
квоты его же подписки (`P2pRelayAccountingService#meterExitSession`) — по
меньшему из двух согласованных отчётов, то есть по той же цифре, за которую
платят владельцу пира.

## Ограничения

- **Только STUN, без TURN** (осознанный выбор, docs §8.1): при симметричном NAT с
  обеих сторон соединение просто не установится — клиент перейдёт к следующему
  пиру. TURN означал бы прогон трафика через нашу же инфраструктуру, то есть ту
  самую стоимость, ради ухода от которой всё и затевалось.
- **Своё устройство не используется**: подключение через себя ничего не обходит,
  а начисление кредита за собственный трафик было бы генератором квоты из
  воздуха. Запрещено на сервере (`Node#isOwnRelayDeviceOf`), а не только скрыто в
  интерфейсе.
- **Гостевые аккаунты** не могут ни раздавать, ни (по тарифной доступности)
  рассчитывать на пул платных реле.
- **Выход — только TCP.** UDP через пира не ходит вообще (см. выше), так что
  QUIC и игровой трафик в этом режиме не работают; DNS закрыт DoH.
- **Согласие одно на оба режима.** Отдельного «только путь, не выход» нет;
  тексты согласия и страница условий говорят это прямо, а не умалчивают.

## Детали, найденные при проверке на живых устройствах

- **На P2P-путях Android-приложение исключено из собственного TUN.** Каждое соединение через пира — новая WebRTC-сессия, которую приложение открывает уже при поднятом TUN; без исключения её STUN/ICE-пакеты уходили в сам туннель. Java-сокеты VPN-приложения нельзя привязать к исходной сети (EPERM), а нативные сокеты WebRTC не защитить через `protect()`, поэтому исключается приложение целиком — трафик пользователей по-прежнему идёт через xray. Проба туннеля в этом режиме идёт через локальный вход xray `probe-in`.
- **Данные в DataChannel — только бинарные сообщения.** Текстовые node-datachannel отдаёт строкой в UTF-8, и бинарный поток ломается.
- **ICE-кандидаты, пришедшие раньше offer, буферизуются** на всех пирах: клиент шлёт offer и кандидаты параллельными запросами.
- **Учёт — по приросту накопительных отчётов**, а не один раз на сессию; трафик выхода списывается с квоты клиента, даже если пиру ничего не начисляется.
- **Запись в gRPC-поток пира сериализована** на сервере и на Android-пире; Android-пир переподключается после обрыва.

## Как это проверено

- `desktop/test/relayClient.test.ts` — **настоящий WebRTC**: мост, подставное
  реле, собранное как настоящие, и TCP-сервер на том конце. Байты проходят весь
  путь туда и обратно, трафик отчитывается, неотвечающее реле бросается, стоп
  закрывает все сессии. Для выхода отдельно: два соединения подряд уходят на
  **разные** адреса из своих SOCKS5-запросов, ответ «успех» приходит только
  после открытия канала, отчёт помечен как exit, а клиент, не говорящий
  SOCKS5, отбрасывается без сессии.
- `desktop/test/xrayConfigFactory.test.ts` — конфиг выхода: socks-outbound на
  мост, VLESS-outbound нет вообще, UDP заблокирован мимо :53, RU-режим
  сохраняется.
- `android/.../P2pRelayConnectorTest.java` — настоящие сокеты, поддельная сессия
  вместо нативного WebRTC: offer называет нужную ноду, ничего не читается из
  сокета до открытия канала, ответ и кандидаты доходят до сессии, дедлайн
  переговоров срабатывает, объём отчитывается. Те же три проверки выхода, что
  на десктопе.
- `server/.../P2pRelayDirectoryTest.java`, `P2pRelayControllerTest.java` — что
  попадает в список и кто имеет право трогать сессию; для выходов отдельно —
  пустой список на пробном тарифе, фильтр по стране, порядок «свежие первыми».
- `server/.../SubscriptionExportServiceTest.java` — P2P-строка в списке
  регионов: ключ `p2p:`, замок на пробном тарифе, своё устройство не
  предлагается, истёкшее окно не показывается, и строка соседа не портит счёт
  и нагрузку строки наших серверов в той же стране.
- `e2e/tests/p2pRelay.spec.ts` — то же против живого сервера.
